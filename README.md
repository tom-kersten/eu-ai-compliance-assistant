# EU AI Compliance Assistant

## What and why

This repository implements a Dutch-language Q&A assistant over four EU legal texts
(AI-verordening, AVG, CRA, Digitale omnibus inzake AI). It is a small, test-driven
proof-of-concept that demonstrates retrieval from a legal corpus, a two-step LLM
pipeline (selection + answer), and a Streamlit frontend for assessors.

## Quickstart (online)

1. Copy the example env and set keys:

   ```bash
   cp .env.example .env
   # edit .env and set LLM_API_KEY and EMBEDDING_API_KEY
   ```

2. Start the online stack:

   ```bash
   make up
   ```

3. Ingest the corpus (once):

   ```bash
   make ingest
   ```

4. Open the frontend at <http://localhost:8501>. Backend health is at
   <http://localhost:8000/health>.

5. Run the evaluation:

   ```bash
   make eval
   ```

Everything runs in Docker. No host Python environment is needed. Run `make help`
for the full list of targets.

## Quickstart (offline)

Self-hosted vLLM. Hardware, quantization, and verified flags are in
[docs/OFFLINE.md](docs/OFFLINE.md).

```bash
cp .env.offline.example .env.offline
# edit .env.offline to match your hardware and models
make up-offline
make ingest ENV_FILE=.env.offline
make test-live ENV_FILE=.env.offline
```

## Architecture

```
Browser -> Streamlit frontend (8501)
        -> FastAPI backend (8000) -> Postgres + pgvector
                                  -> Embedding endpoint (hosted or vLLM)
                                  -> LLM endpoint (hosted or vLLM)
```

The backend streams progress to the frontend as Server-Sent Events. Details:
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Scope and behavior:
[docs/REFERENCE.md](docs/REFERENCE.md). Prompt requirements:
[docs/PROMPT_SPEC.md](docs/PROMPT_SPEC.md).

## Design decisions and trade-offs

- Stateless backend; session state lives in the Streamlit frontend.
- Postgres with pgvector, exact cosine search, fixed embedding dimension (2000).
- Two LLM calls per question maximum: selection (one call) and answer (one call).
- Prompts written in English; UI and outputs in Dutch.
- No third-party orchestration frameworks; small, testable functions.
- Provider behavior is verified against the live API before it is coded against
  ([docs/PROVIDER_NOTES.md](docs/PROVIDER_NOTES.md), regenerated by
  `make verify-providers`).

## Eval results

See [docs/EVAL_RESULTS.md](docs/EVAL_RESULTS.md) and the latest report in
`eval/reports/` for the recorded evaluation metrics and the configuration used.
The README does not introduce new numbers; it links to the canonical report files.

## Known limitations

- Single-turn evaluation set only; multi-turn behavior is not fully validated.
- The retrieval threshold was tuned on a small eval set; some misses remain
  (notably Q06–Q08 retrieval gaps recorded in the eval reports).
- LLM output is not deterministic, so individual eval questions can flip between
  runs (Q05 in particular; see the eval report).
- Offline (vLLM) profile is documented but unverified without GPU hardware.
- The corpus is not a consolidated single document; provenance and versioning
  are manual via the manifest.

## Next steps at production scale

- Consolidate and version the legal texts; sign each snapshot.
- Add reranking or a hybrid sparse + dense retrieval layer.
- Multi-turn evaluation and user studies for clarifying questions.
- Persistence, authentication, and observability for production APIs.

## Tests and continuous integration

These need no keys or GPUs:

```bash
make lint            # ruff check and format check (backend, eval, frontend)
make test            # backend unit, api, and db suites
make test-frontend   # frontend suite
```

Opt-in, against real providers (needs keys, costs money):

```bash
make test-live
make eval
```

GitHub Actions runs `make lint`, `make test`, and `make test-frontend` on every
push and pull request, and validates the compose file for both profiles. See
[.github/workflows/ci.yml](.github/workflows/ci.yml). Evaluation reports are
written to `eval/reports/` (git-ignored).
